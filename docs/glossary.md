# 用語集（Glossary）

> このハーネスが使う言葉を、**普通の日本語で**説明する。
> 分からない言葉が出てきたら、まずここを見る。ここに無ければ Claude に聞けば、説明したうえでここに追記される。
>
> 更新するのは `@idea-chair` とメインスレッド。**新しい用語を使ったら、必ずここに追記する。**

---

## 1. 判定に関する言葉

### DECISION（ディシジョン／判定）
毎ラウンドの最後に必ず1つ選ばれる結論。次の5つしかない。

| 判定 | 普通の言葉でいうと | 次にやること |
|---|---|---|
| **BUILD** | 作っていい | 開発に移る |
| **ITERATE**（イテレート） | 問題は本物。でも案の形が悪いので直す | 案を修正してもう一度分析 |
| **VALIDATE**（バリデート） | まだ何も確かめていないので、確かめてから | 外に出て人に聞く・調べる |
| **PIVOT**（ピボット） | 方向を変える。ゼロには戻らない | 別のターゲットや別の問題へ作り直す |
| **KILL**（キル） | この案は作らない | やめる。学びだけ持っていく |

**KILL は失敗ではない。** 3ヶ月作ってから気づくはずだったことに、最初の週で気づけたということ。

### CRITICAL 仮説（クリティカル・かせつ）
「これが間違っていたら、この案は根本から成立しない」という前提。3つ以内に絞る。
例:「習慣化に挫折した人は、それをアプリで解決したいと思っている」

### Critical Risk（クリティカル・リスク）
採点の8項目のうち、**満点の40%未満しか取れなかった項目**。
1つでもあると `BUILD`（作っていい）は出ない。総合点が高くても同じ。

## 2. 証拠（Evidence）に関する言葉

### Evidence Level（エビデンス・レベル／証拠の強さ）
その主張が、どれくらい現実で確かめられているかの段階。**L0 が一番弱く、L4 が一番強い。**

| レベル | 意味 | 例 |
|---|---|---|
| **L0** | まだ誰にも確かめていない。AIの推測だけ | 「困っている人はいるはず」 |
| **L1** | ネットや市場で調べた情報 | 競合の価格表、App Store の順位 |
| **L2** | 実際のユーザーが**口に出した**こと | インタビュー、レビューの本文 |
| **L3** | 実際のユーザーが**やった**こと | ページを見た人の登録率、実際の利用ログ |
| **L4** | 実際に**お金を払った・使い続けた**こと | 課金、翌週も使っているか |

**あなた自身の「絶対いける」という確信も L0 です。** 作り手の実感は証拠として数えない。

### Evidence Cap（エビデンス・キャップ／証拠による点数の上限）
「まだ確かめていないことに、高い点数を付けない」ための仕組み。
証拠が L0（推測だけ）なら、その項目は満点の40%までしか点が入らない。

そのため **1回目の分析は、どんなに良い案でも合計40点前後が上限**になる。
これは案が悪いという意味ではなく、**まだ何も確かめていない**という意味。

### n=3 / n=30
話を聞いた人数。`n=3` は3人に聞いたということ。**3人と30人を同じ扱いにしない**ためにいつも書く。

## 3. 案の中身に関する言葉

### Core Problem（コア・プロブレム／中心の問題）
このアプリが解決する問題。**1つだけ。**

### Core Action（コア・アクション／中心の行動）
ユーザーがこのアプリでやる中心的な行動を、**動詞1つ**で表したもの。
例:「記録する」「探す」「診断する」。これが2つ以上あるアプリは、たいてい大きくなりすぎている。

### Target User（ターゲット・ユーザー）
誰のためのアプリか。**年齢や職業ではなく「どういう状況にいる人か」で定義する。**
例:「20代女性」ではなく「転職を考えていて、自分の向き不向きが分からず止まっている人」。

### Value Proposition（バリュー・プロポジション／提供価値）
「何と比べて、どれくらい良くなるのか」。「便利になります」は価値提案ではない。

### MVP（エムブイピー／Minimum Viable Product）
**確かめたいことを確かめられる、最小の形**。「機能を減らしたアプリ」ではなく「検証装置」。
このハーネスでは4〜8週間で作り終わる範囲を目安にする。

### Aha Moment（アハ・モーメント）
ユーザーが初めて「これは良い」と実感する瞬間。ここに早く到達できないアプリは続かない。

### Activation（アクティベーション）
インストールした人が、Aha Moment までたどり着くこと。

### Retention（リテンション／継続）
**2回目以降も使い続けてもらえるか。** 「1回使って終わり」のアプリは事業にならない。

### Distribution（ディストリビューション／どうやって知ってもらうか）
作った後、ユーザーにどうやって届けるか。
**個人開発が失敗する最大の理由は、作れなかったことではなく、誰にも知られなかったこと。**

### Monetization（マネタイゼーション／収益化）
誰が、なぜ、いくら払うのか。

### Differentiation（ディファレンシエーション／差別化）
既存の代替手段より明確に良い理由。「UIが使いやすい」「AIを使っている」だけでは差別化ではない。

### Current Alternative（カレント・オルタナティブ／今どうしているか）
そのユーザーが、**このアプリが無い今、その問題をどう処理しているか。**
このハーネスが最も重視する項目。代替手段が何も無い問題は、たいてい問題ではない（誰も困っていない）。

### Switching Cost（スイッチング・コスト／乗り換えの手間）
今のやり方をやめて、このアプリに移るときにユーザーが払う手間。

### Jobs to be Done（ジョブズ・トゥ・ビー・ダン）
「ユーザーはこのアプリを、何を片付けるために雇うのか」という考え方。
機能ではなく、ユーザーが達成したい用事の側から考える。

### Paywall（ペイウォール）
無料で使える範囲と、お金を払わないと使えない範囲の境目。

### Unit Economics（ユニット・エコノミクス／1人あたりの採算）
ユーザー1人あたり、いくら費用がかかり、いくら入ってくるか。
AI を使うアプリでは、**API の原価が月額料金を超えていないか**が必須の確認項目。

### Feature Bloat（フィーチャー・ブロート／機能の膨張）
機能を足しすぎて、何のアプリか分からなくなること。このハーネスが最も強く警戒する状態。

## 4. ID（記号）の読み方

このハーネスは記録のために記号を使う。**記号だけで書かれることは無く、必ず内容が併記される。**

| 記号 | 意味 | 書かれ方の例 |
|---|---|---|
| **OPP-1** | Opportunity（改善案）の1番目 | OPP-1「手入力をやめて写真から自動で読み取る」 |
| **EXP-001** | Experiment（検証実験）の1番目 | EXP-001「Discordで3人に挫折理由を聞く」 |
| **A1** | Assumption（仮説）の1番目 | A1「挫折した人はアプリで解決したいと思っている」 |
| **v001** | アプリ案のバージョン1 | `docs/versions/idea-v001.md` |
| **Round 1** | 1回目の分析 | Intake（最初の聞き取り）は Round 0 で、数えない |

## 5. 改善の方向を表す言葉

### 5つの方向
案をどう変えるかの分類。

| 方向 | 意味 |
|---|---|
| **KEEP** | そのまま維持する |
| **ADD** | 足す（**1ラウンドに最大1つまで**。足すなら同時に何か削る） |
| **CHANGE** | 変える（入力の仕方、使うタイミング、対象ユーザーなど） |
| **REMOVE** | 削る（機能だけでなく「ユーザーがやってくれるはず」という前提も削る） |
| **REPLACE** | 別のやり方に置き換える（手入力 → 自動取得 など） |

### 3つの深さ
案をどれくらい大きく変えるか。

| 深さ | 意味 |
|---|---|
| **Incremental**（インクリメンタル） | 小さく改善する。元に戻せる |
| **Adjacent**（アジャセント） | 今の資産を活かして、少し違う方向へ広げる |
| **Radical**（ラディカル） | 前提そのものを疑う。**採用には L2 以上の証拠が必要** |

### 純増禁止
`ADD`（機能を足す）を採用するなら、同じラウンドで `REMOVE` か `REPLACE` も1つ以上採用しなければならない。
**機能が増え続けることを防ぐための歯止め。**

## 6. 検証（実験）に関する言葉

### Success Criteria / Failure Criteria（成功条件／失敗条件）
実験をやる**前に**数字で決めておく合格ライン・不合格ライン。
後から解釈を変えられる実験は意味がないため、必ず先に決める。

### Landing Page（ランディングページ／LP）
アプリの説明だけを載せた1ページのウェブページ。まだ中身は作らない。
「使いたいと思う人がいるか」を、作る前に確かめるために使う。

### Waitlist（ウェイトリスト／順番待ち登録）
LP に「できたら教えて」とメールアドレスを登録してもらう仕組み。登録率が L3 の証拠になる。

### CVR（シーブイアール／Conversion Rate・転換率）
ページを見た人のうち、実際に登録・購入した人の割合。100人来て2人登録なら CVR 2%。

### Fake Door Test（フェイクドア・テスト）
まだ無い機能のボタンだけを置いて、何人が押すかを見る方法。
「欲しいと言うか」ではなく「実際に押すか」を測れる（L3の証拠）。

### Pre-mortem（プレモーテム／事前検死）
「1年後、このアプリは失敗した。何が起きたのか」を**先に**書いてみる方法。
成功する理由より、失敗した後の景色から逆算するほうが穴が見つかる。

### UGC（ユージーシー／User Generated Content）
ユーザーが作ったコンテンツ。これが検索に載ると、宣伝しなくても人が来る構造になる。

## 7. このハーネスの仕組みの言葉

### ハーネス
Claude Code に「どう振る舞うか」を指示する設定一式のこと。このプロジェクトでは `CLAUDE.md` と `.claude/agents/` がそれにあたる。

### Agent（エージェント）
特定の役割だけを担当する Claude。このハーネスには8体いて、それぞれ別の視点から分析する。

### Intake（インテイク／最初の聞き取り）
アプリ案を入れた直後の、最大5問の質問。ここは Round 0 で、ラウンド数に数えない。

### Handoff（ハンドオフ／引き継ぎ）
`BUILD`（作っていい）が出たときだけ作られる、開発用の仕様まとめ（`docs/handoff.md`）。
このハーネスはコードを書かない。実装は別のハーネスに渡す。

### Stop Conditions（ストップ・コンディション／停止条件）
アイデアをこね続けないための打ち切りルール。
例:「新しい証拠が無いのに再分析しない」「同じ仮説の検証に2回連続で失敗したら3回目はやらない」。

### 開発手段
アプリのコードを、誰が・どうやって書くか。**自分で書く / AI にほぼ任せる / 併用** のどれか。
`docs/idea.md` の「作り手の制約」に記録する。ここが変わると `@technical-analyst` の見積もりの前提が変わる。

### 実装時間 / 判断時間 / 運用時間
開発にかかる時間の3つの内訳。**合計だけで判断すると読み違える。**

| 内訳 | 中身 | AI にほぼ任せると |
|---|---|---|
| 実装時間 | コードを書く | 大きく減る |
| 判断時間 | 仕様を決める、生成物をレビューする、詰まりを解く | あまり減らない |
| 運用時間 | リリース後の保守、サポート、障害対応 | 減らない |

**実装が安くなることは、大きく作ってよい理由にはならない。**
MVP が膨らむと、運用コストとサポート負荷だけが実サイズで残る。

### agent-quartet-harness
実装を担当する別の Claude Code ハーネス。このハーネスで `BUILD`（作っていい）が出たあと、
`docs/handoff.md` を渡して仕様策定 → 実装 → デザイン → QA を任せる先。
